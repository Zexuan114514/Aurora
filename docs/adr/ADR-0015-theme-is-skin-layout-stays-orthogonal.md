# ADR-0015：主题＝皮肤，布局保持正交（不采用一主题一布局）

## 状态

已接受（2026-09-27）。补充 [ADR-0013](ADR-0013-frontend-build-chain-and-themes.md)
「五套风格共用一个 DOM」那一条：这次把**不做什么**也写清楚，避免反复摇摆。

## 背景

同类开源启动器的常见做法是**一主题一布局**：每套主题自带一个 Layout 组件与一份主题 CSS
（对照项目的 6 个 Layout 组件 + 5 份 22–46 KB 主题样式）。跟着走看着"更有诚意"，
但代价在单人维护的盘子里非常具体：

1. **每个布局改动都要在多处验证**。对照项目里已经出现「只有某个主题复现」的封面尺寸异常、
   滚动条丢失这类 bug —— 它有社区兜底，Aurora 没有。
2. **Aurora 的视觉身份在几何，不在皮肤**：大厅环形队列的 `rotateY` + 透视 + 首尾相接是原创识别度，
   `layout.css` 只有一份；`tools/e2e.py` 的环形判据（`ring/347.0`、`±16/283.2`、`32/232.5`）
   与 `tools/visual.py` 的 35 张主题矩阵都压在这套几何上。多布局会让这套量化验收塌掉。
3. **现在就是正交结构**：五套风格 × 三种大厅布局（环形 / 平铺横滑 / 大图侧列表），
   且有配套守卫 —— 令牌契约、皮肤行数上限（≤200）、选择器必须挂在自己的 `[data-style="…"]` 下、
   圆角只能走 `--r-*` 令牌且档位单调、`--fx-blur` 只允许极光玻璃非零。
   这些守卫是**为「皮肤可扩展」量身定做**的。

## 决策驱动

- **D1 单人维护 + 社区贡献**：加主题必须是小而局部的改动，不能是"再写一套页面"。
- **D3 真机现场性**：验收判据（环形几何 + 35 张矩阵 + 区分度）必须可量化、可回归。
- 区分度靠 **令牌与签名**，不靠改布局。

## 考虑过的选项

1. **一主题一布局**（学对照项目）：视觉差异最大，但等于推倒重来 + 维护面 ×N。
2. **主题＝皮肤，布局保持正交**（选它）：加主题 = 加令牌 / 签名 / 按钮皮肤三份 CSS，
   几何与全部探针 id 冻结。
3. **把「布局」提升为与「皮肤」并列的第二个维度**（`data-layout` × `data-style`）：
   正交得彻底，但组件要同时面对 N×M 组合，收益远小于成本。

## 决定

**选 2**：主题就是皮肤。加一套主题的正确姿势是三份 CSS
（`<theme>.tokens.css` 深/浅两个块 + `<theme>.skin.css` 结构性签名 + `<theme>.buttons.skin.css` 按钮语言），
外加主题矩阵的一行；**不改组件几何、不动任何探针 id**。

选项 3 明确记为**将来若真要"主题改布局"时的唯一正确方向**（把布局提升为并列维度，
而不是把布局焊进主题），当前不做。

## 后果

- ✅ 加主题的贡献门槛低到"三份 CSS + 一行矩阵"，与 [CONTRIBUTING](../../CONTRIBUTING.md) 的贡献路径一致。
- ✅ `layout.css` 只有一份，环形几何的 e2e / visual 判据继续有效；主题矩阵按张重录即可回归。
- ✅ 守卫可以继续加码（行数上限、选择器作用域、圆角单调、模糊口径），
  这些都是**皮肤可扩展**的护栏，不是布局的。
- ⚠️ 主题之间的差异只能来自令牌、签名与按钮语言：`tools/visual.py` 的深色两两色差
  **≥20** 是硬指标，新主题必须过（当前五套 23.9）。
- ⚠️ "某套主题换个完全不同的布局"这类诉求会被拒；要做得先按选项 3 立新 ADR，
  并给出 N×M 组合的验收方案。

## 后续动作

- 新增主题的 PR 验收：`check_theme_contract` + `tools/visual.py` 矩阵张数 +1 且逐张在容差内、
  区分度 ≥20，`run_all` / `pytest` 全绿。
- 主题模板与预览（`docs/theme-templates/README.md`）保持"三份 CSS"的说法；
  若发现别处还在教"一主题一布局"，以本 ADR 为准。
