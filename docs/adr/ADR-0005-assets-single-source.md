# ADR-0005：资产单一来源（本地静态资源服务）

## 状态

已接受。

## 背景

用户素材（背景图、自定义封面、自定义图标）原图存在 `data/{backgrounds,covers,icons}`，
为了让页面能访问，启动时被复制到 `gl/web/{userbg,usercovers,usericon}`；打包脚本必须显式排除这些副本，
否则用户素材会被打进发布包（历史上已经踩过这个坑）。这造成同一份数据两个位置、两份真相。

## 决策驱动

- 资产单一来源，消除「复制—过期—误打包」链路。
- 单文件 exe 下 `web/` 是临时解压目录，写入副本的行为本身就不稳定（C5）。
- 免安装、零依赖（标准库 `http.server` 足够）。

## 考虑过的选项

1. **保留复制机制**（现状）。
2. **自建本地静态 + 资源服务**：`/` 服务随包前端，`/assets/` 映射数据目录，仅监听 127.0.0.1。
3. **直接用 `file://` 引用数据目录**：依赖内核的文件访问策略，跨内核不确定。

## 决定

选择 **2**。服务只允许 `GET` / `HEAD`，只绑定 `127.0.0.1`，端口取空闲端口；
路径规范化后必须在白名单目录内；`/state/*` 与任何路径穿越返回 403/404；删除 `sync_user_assets`
与 `web/{userbg,usercovers,usericon}` 目录及其打包排除项。

## 后果

- ✅ 用户素材只有一份，不会再出现「改了图不生效」或「素材进了发布包」。
- ✅ 前端模块化后资源路径统一（`/assets/...`），缓存策略集中控制。
- ⚠️ 新增一个本地服务 = 新的安全面，必须有越权/穿越用例（R4）。
- ⚠️ 双内核行为需要实测；若某内核不兼容，回退到选项 1（保留一个版本的开关）。

## 后续动作

- P5 验收：双内核下封面/背景/自定义图标可访问；越权与穿越被拒。
- 复核 `tools/build_exe.py` 的资源清单排除项是否仍然必要（迁移完成后可简化）。
