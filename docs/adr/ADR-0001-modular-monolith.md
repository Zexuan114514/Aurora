# ADR-0001：采用模块化单体，不拆进程/服务

## 状态

已接受（设计基线；实施从 P0 开始，见 `13-roadmap.md`）。

## 背景

Aurora 是单机桌面启动器，需要长期在用户机上与游戏、TextractorCLI、Locale Emulator 共存。
当前代码功能完整但无结构：桥接与业务同体、纯规则与 IO 混排、数据单文件全量重写。
同时存在三类高风险代码：调试器钩子查找、只读内存扫描、WinRT OCR。

## 决策驱动

- 免安装单文件 exe 的分发形态（D4）。
- 单人维护 + 社区贡献的协作模式（D1）。
- 运行环境的外部依赖一律不打包（C3）。
- 目前没有任何故障数据支持「必须进程隔离」。

## 考虑过的选项

1. **模块化单体 + 端口适配**：单进程，分层与契约治理。
2. **按技术分层的单体**：只分层，不引入端口与规则包。
3. **关键子系统进程隔离**：vntext / 翻译跑子进程。
4. **桌面壳 + 常驻后台服务**：本地服务 + 多窗口。

## 决定

选择 **1**。`ui → app → domain`，`infra` 实现端口，`platform` 提供 Win32 原语，组合根只有一个 ——
设计稿里叫 `bootstrap.py`，落地时留在 `gl/api.py` 的 `Api()`（P3.5 收口后 `api.py` 只剩 196 行装配/生命周期）；
不引入 IPC、不引入常驻服务。评估细节见 `01` / `03` / `04`。

## 后果

- ✅ 运行形态不变，发布与排错复杂度不变；纯规则可离线测试；社区扩展有落点。
- ⚠️ 调试器 / 内存扫描异常仍可能带走主进程；靠「只在需要时运行 + 只读 + 超时」缓解。
- ⚠️ Python 无编译期边界，需要 AST 守卫进 CI 才能长期成立。

## 后续动作

- 采集 exe 体积、冷启动耗时、崩溃日志作为基线（P0）。
- 若出现「主进程被本仓库 native 代码打崩 ≥ 2 次」，重新评估选项 3。
- 若出现「后台常驻 / 多窗口 / 第三方调用 Aurora 能力」的真实需求，重新评估选项 4。
