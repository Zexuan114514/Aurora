# ADR-0004：数据分账与 schema 版本化

## 状态

已接受。

## 背景

现状是单一 `data/library.json`（297 KB / 24 游戏 / 60 字段 / 39 项设置），`Library` 类的任何一次
`update` / `set_setting` 都会全量重写整个文件；文件里只有 `"version": 1`，没有迁移器、没有备份、
没有字段校验。会话历史直接内嵌在每个游戏记录里。

## 决策驱动

- 写放大：改一个设置要重写全部游戏（`10` H1）。
- 可恢复性：强杀进程、迁移失败、文件损坏都要能回到可用状态。
- 未来格式演进（插件配置、UI 偏好、规则包元数据）。

## 考虑过的选项

1. **保持单文件，只加 `schema_version` 与备份**。
2. **分账为四个真相文件**（settings / library / sessions / glossary）+ 迁移器 + 单写者。
3. **迁移到 SQLite**（标准库 sqlite3）。

## 决定

选择 **2**。布局与字段表见 `contracts/data-schema-v2.md`：`state/settings.json`、`state/library.json`、
`state/sessions.jsonl`、`vntext/glossary.json`；写入走单写者 + 原子替换 + 去抖；迁移单向 1 → 2，
自动备份到 `state/backup/`，支持 `--check-migration` 干跑。

## 后果

- ✅ 设置写入降到常量级；会话记录追加写；迁移与回滚有明确路径。
- ✅ 用户仍可用文本工具查看/备份自己的数据（保持「可见的 JSON」这一性格）。
- ⚠️ 迁移必须一次做对：用真实库夹具做字段全等断言，失败即中止且不写新文件。
- ⚠️ v1 程序读 v2 会起空库 → 必须在界面与文档里给回滚三步法。

## 后续动作

- 选项 3（SQLite）保留为「库规模 > 500 款且查询需求出现」时的评估方向，届时另立 ADR。
- 迁移器与备份策略纳入 P2 验收；导出默认剥离密钥（与 ADR-0011 配套）。
