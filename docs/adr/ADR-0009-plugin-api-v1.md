# ADR-0009：插件 API v1（进程内、无沙箱）

## 状态

已接受。

## 背景

项目要接受社区贡献，但当前扩展点只有「改核心代码」：新增资料源要动 `gl/sources/manager.py` 的
`BUILTIN` 表，新增翻译引擎要动 `gl/translate.py` / `gl/linetrans.py`。
同时运行时零新增依赖、免安装、单机运行（ADR-0003）。

## 决策驱动

- 扩展点必须能对外文档化（社区可读、可测试）。
- 零新增依赖 → 不能引入插件框架或沙箱运行时。
- 信任模型要诚实：插件与宿主同权限，能读文件、能联网。

## 考虑过的选项

1. **不做插件机制**，只接受核心 PR。
2. **目录加载的进程内插件**（`data/plugins/<kind>/<id>/`）+ manifest + `api_version` 门禁。
3. **子进程/隔离沙箱插件**：与 ADR-0001 冲突，且零依赖下无法安全实现。

## 决定

选择 **2**。契约见 `contracts/plugin-api-v1.md`：`api_version` 主版本必须匹配、次版本不得高于宿主；
manifest 声明 `kind` / `id` / `entry` / `permissions`（自述，非强制）；加载用
`importlib.util.spec_from_file_location`，不改 `sys.path`；每次调用包裹异常与超时，
连续 3 次失败自动禁用；**明确声明不做沙箱**，界面与文档如实告知用户。

## 后果

- ✅ 贡献者路径清晰：插件 = 一个目录 + 一份 manifest；规则包 = 一个 JSON。
- ✅ 宿主不会被插件异常搞崩（内存回收与线程回收不保证，文档写明）。
- ⚠️ 用户需要自行信任插件来源 → 设置页展示 `permissions` 与来源路径。
- ⚠️ 加载失败、版本不兼容、自动禁用等状态必须有界面呈现，否则用户会以为「插件没生效」。

## 后续动作

- P6 实现加载器 + 状态展示 + 用 fake 插件跑通「发现 → 注册 → 失败 → 禁用」。
- 编写面向贡献者的最小示例（资料源 / 翻译引擎），放在 `contracts/` 或 `docs/` 中。
