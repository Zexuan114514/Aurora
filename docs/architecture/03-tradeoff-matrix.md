# 03 权衡分析（tradeoff-analysis-writer）

## Summary

把 `01` 的 4 个选项放进同一张准则表里算账。结论：**选项 A（模块化单体 + 端口适配）** 在
「维护成本 / 迁移风险 / 社区扩展 / 分发形态」四项上同时占优，只在「故障隔离」这一项输给选项 C，
而这一项当前没有被实测数据支持（见 `12` 风险 R7）。

## 评价准则

| 准则 | 权重 | 含义 |
| --- | --- | --- |
| 维护成本 | ★★★ | 单人改一个功能要碰多少文件、要理解多少上下文 |
| 迁移风险 | ★★★ | 改造期间用户数据与既有功能退化的可能性 |
| 分发形态 | ★★★ | 是否保持单 exe 免安装、零新增运行时依赖 |
| 社区扩展 | ★★☆ | 外部贡献资料源 / 翻译引擎 / 引擎规则的落地成本 |
| 可测试性 | ★★☆ | 无游戏、无网络、无 Textractor 时能验证多少 |
| 故障隔离 | ★★☆ | 高风险代码（调试器、内存扫描、OCR）崩溃的波及面 |
| 性能上限 | ★☆☆ | 大量游戏 / 高频事件下的天花板 |
| 一次性投入 | ★★☆ | 需要多少迁移工作量才能到位 |

## 权衡矩阵

| 准则 | A 模块化单体 + 端口 | B 技术分层单体 | C 关键子系统隔离进程 | D 壳 + 后台服务 |
| --- | --- | --- | --- | --- |
| 维护成本 | 低（边界清楚，规则可定位） | 中（分层但无契约） | 高（IPC + 生命周期 + 打包） | 高（多进程 + 端口 + 鉴权） |
| 迁移风险 | 低（运行形态不变，逐阶段迁移） | 低（改动小） | 中（文本链路全部要走 IPC） | 高（发布形态重做） |
| 分发形态 | 保持单 exe / 零依赖 ✅ | 保持 ✅ | 单 exe 但多子进程、调试变难 ⚠ | 需要服务与端口管理 ❌ |
| 社区扩展 | 端口 + 规则包 + manifest ✅ | 要动核心文件 ❌ | 端口可用，但插件跨进程复杂 ⚠ | 可做，但门槛与安全面都上升 ⚠ |
| 可测试性 | 纯逻辑可离线单测 + fake 适配器 ✅ | 仍需真机 ⚠ | 需要进程协议测试 ✅ | 需要接口级测试 ✅ |
| 故障隔离 | 同进程（调试器崩溃会带走主进程）⚠ | 同进程 ⚠ | 最强 ✅ | 强 ✅ |
| 性能上限 | 足够（瓶颈在库文件与事件频率，非进程模型） | 相同 | 略差（IPC 往返） | 相同 |
| 一次性投入 | 中（P0–P7） | 小 | 大 | 很大 |
| 结论 | **推荐** | 不足 | 触发条件式备选 | 仅在方向变化时重估 |

## 叙事式理由

1. **真正的成本在「改动风险」，不在性能**。当前 24 款游戏的库、每秒个位数的翻译事件，
   离任何进程模型的性能上限都还很远；而每次改清洗规则都要在 1944 行文件里定位、每加一个资料源
   都要碰核心文件，是每天都在付的成本。
2. **单 exe 是产品的性格**。选项 C/D 都会让「拷一个 exe 到任何地方就能跑」变成需要解释的事情，
   这直接违背 D4；除非实测证明调试器/扫描会稳定打崩主进程。
3. **社区贡献的入口必须是声明式的**。引擎规则、外挂钩子码这类内容最适合 JSON 规则包 + 指纹匹配，
   贡献者不需要读 2000 行 Python；这是选项 A 特有的收益，也是 `docs/engines.md` 目前最大的维护痛点
   （文档表格与代码里的实测记录已经存在两份）。
4. **测试网决定了重构能走多远**。选项 A 把纯规则下沉后，`tools/*-report.txt` 里的真机样本可以直接
   变成回归断言；没有这层网，P3–P6 的任何搬迁都是在赌。

## Recommendation

- **Chosen option**：A（见 `04` 的判定与 `05` 的落地规则）。
- **What must be watched**：
  - 迁移期是否被「顺手再拆一层」诱惑而失控（P0–P7 之外的需求一律排队）。
  - AST 守卫是否真的拦下了越界 import（P7 验收：故意引入一次违规必须让 CI 变红）。
  - `window.__aurora` 测试面是否保住（P4 验收：`tools/e2e.py` 90 项全过）。

## Evidence vs assumptions

- **证据**：分发形态、依赖数量、外部工具策略都是当前仓库的硬事实（见 `README.md` 基线表）；
  进程隔离的收益在仓库里没有对应故障记录（`config.log` 用途、`hookfinder` 仅在手动触发时运行）。
- **假设**：用户规模与游戏库规模在未来 12 个月内不会出现数量级变化；若出现，`10` 的阈值会先被触发。
- **反向证据的寻找方式**：若连出现两次「主进程被 native 代码打崩」的日志，选项 C 立即重新评估（R7 的实验）。

## Risks or tradeoffs

| 被放弃的东西 | 代价 | 何时值得换回来 |
| --- | --- | --- |
| 进程级故障隔离 | 调试器/内存扫描异常可能带走进程 | 主进程崩溃成为 Top1 反馈 |
| 多窗口 / 常驻服务扩展性 | 后台能力无法被第三方复用 | 出现「把 Aurora 当服务用」的真实需求 |
| 一致的运行时抽象 | 未来跨平台要重做 | 明确要做跨平台（当前不在范围） |
