# 02 质量属性场景（quality-attribute-scenario-writer）

## Summary

把「要更快 / 更稳 / 更好改」这类目标翻译成 **14 条可度量、可回归**的场景。每条都绑定现有的验证手段
（`tools/` 下的探针脚本）或新增的离线测试，避免架构目标停在形容词层面。

## 场景表

| # | 属性 | 源 / 刺激 | 环境 | 响应 | 度量 | 优先级 |
| --- | --- | --- | --- | --- | --- | --- |
| Q1 | 性能 | 用户双击 exe | 本机 SSD、库内 24 游戏、断网 | 大厅可交互 | 冷启动到首帧可交互 ≤ 1.5s；启动流程不得做网络请求 | 高 |
| Q2 | 性能 | 用户按 `←/→` 切封面 | 大厅、库内 ≤ 200 游戏 | 焦点切换动画 | 单帧 ≤ 16ms，切换不依赖网络 | 高 |
| Q3 | 正确性 | 连续翻页 20 句 | 真机 + Textractor 钩子 | 每句都有译文 | 丢句 0；同句只翻一次；顺序与原文一致 | 高 |
| Q4 | 性能 | 新台词进入翻译队列 | LLM 接口正常（1–3s/句） | 悬浮窗出现首 token | 首 token ≤ 2s 出现事件；不掐断上一句请求 | 高 |
| Q5 | 数据完整性 | 任意时刻强杀进程 | 游戏运行中 / 翻译中 | 重启后库可读 | 库文件不损坏；游玩时长误差 ≤ 30s（心跳粒度） | 高 |
| Q6 | 可迁移性 | 首次用 v1 库启动 | `data/library.json`（24 游戏 / 60 字段 / 39 设置） | 自动迁移到 v2 | 游戏数、ID、play_time、play_count、sessions、分类、图片字段全等；失败可回滚 | 高 |
| Q7 | 可维护性 | 开发者新增一个资料源 | 离线环境 | 只加 1 个文件 + 1 段 manifest | 不修改核心文件；CI 契约与层级检查通过 | 高 |
| Q8 | 可测试性 | CI 跑离线测试 | 无游戏、无 Textractor、无网络 | 核心用例全绿 | 用例数 ≥ 80；总时长 ≤ 3 分钟；覆盖清洗规则 / 打分 / 结算 / 迁移 / 契约 | 高 |
| Q9 | 可用性 | TextractorCLI 缺失或崩溃 | 真机 | 自动降级 | 缺失 → 提示并回退 OCR；崩溃 → 主进程存活并给出状态 | 高 |
| Q10 | 可用性 | 日语 OCR 组件未安装 | 真机 | 明确指引 | 面板给出「去哪装」的可点击指引，不静默失败 | 中 |
| Q11 | 安全性 | 页面或外部进程尝试读数据目录 | 运行时 | 请求被拒 | 仅监听 127.0.0.1；仅 GET/HEAD；`/state/*` 与路径穿越返回 403/404 | 高 |
| Q12 | 安全 / 隐私 | 用户导出游戏库 | 已配置 API Key | 导出文件不含密钥 | 导出 JSON 中 `translate_api_key` 为空且写入 `schema_version: 2` | 中 |
| Q13 | 可观测性 | 用户反馈「译文不对」 | 任意 | 可定位 | 一键诊断包含版本、能力探测、最近 200 行结构化日志；日志字段含 game_id / engine / 线程 key | 中 |
| Q14 | 兼容性 | 重构后前端升级 | 任意 | 契约零漂移 | 桥接方法名 105 + 悬浮窗 4、事件主题 14 与快照 diff = 0 | 高 |

## 度量方式与工具

| 场景 | 现在怎么量 | 目标形态怎么量 |
| --- | --- | --- |
| Q1 / Q2 | 人工感受；`tools/snap.py` + `tools/analyze.py` 做像素检查 | 启动打点日志（`boot.*` 阶段耗时）+ `tools/e2e.py` 的布局断言 |
| Q3 / Q4 | `tools/vntext_live.py` 真机连翻 + 报告文本 | 同上，另加事务计数（下发 / 去重 / 合并 / 翻译 / 完成） |

| Q11 | 无 | 本地 HTTP 服务的越权/穿越用例 |
| Q14 | `tools/check_bridge.py` | 契约快照 diff（`contracts/bridge-contract.json`） |

## Findings（现状差距）

> **P0 时期的记录**（2026-09-20）。下面第 1、4 两条后来已经不成立：P1 起纯逻辑有金样本断言，
> P3/P6/P7 之后 CI 跑的是 `run_all` 十项 + `pytest` + 打包 dry-run + 诊断包；
> 契约守卫也从「正则比对」升级成 `tools/checks/check_contract.py` 的快照逐点比对，
> `tools/check_bridge.py` 只留作人读版。细节见 [`p7-governance.md`](p7-governance.md) 与它的第 7 节（复核补丁）。

1. **可测试性是最大缺口**：目前 20+ 个探针脚本全部需要真机 / 联网，CI 只能跑 `check_bridge.py`。
   纯逻辑（清洗、打分、结算）没有一行离线断言 —— 这正是 P1 先做 `domain` 的原因。
2. **性能没有基线**：没有启动打点，也没有「多少游戏时前端开始卡」的数据；`10` 给出阈值假设与测量点。
3. **数据完整性靠运气**：写入是「临时文件 + 替换」，但全量重写发生在每次设置变更，且没有备份/校验。
4. **契约靠人肉**：`check_bridge.py` 用正则，且不在 CI 里。

## Evidence vs assumptions

- **证据**：Q3 / Q4 / Q9 的度量来自 README 里已有的真机实测结论（KiriKiriZ / BGI / Escu:de / WillPlus / Artemis）；
  Q14 的数字来自 `contracts/bridge-contract.json` 快照。
- **假设**：玩家库规模中位数在 20–100 款之间（当前 24 款），因此 Q2 的 200 款作为上界；
  Q1 的 1.5s 是按当前实现（无网络阻塞的启动路径）留出的回归护栏，不是新性能要求。
- **不确定**：Q4 的 2s 依赖用户所用 LLM 服务的首 token 延迟，超时场景按 `08` 的失败路径处理（保留上一句译文）。

## Risks or tradeoffs

- 度量过严会让「真机现场」束手束脚：Q3 这类指标只在发布前手动矩阵里卡，不进每次 CI。
- 度量过松等于没有：Q5 / Q6 / Q14 必须做成自动化，否则重构期没有安全网。
- 指标之间会互相拉扯：为了 Q11 收紧本地服务会牵动 Q1（多一次探测），取舍写在 `03`。
