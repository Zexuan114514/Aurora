# 响应慢 / 卡死诊断（2026-09-21 用户实测反馈）

用户现场：

1. 少女之剑：启动时专用 hook 没「自动带出」，面板里迟迟没有 userhook，点「发送」/「存为专用
   hook 码」没反应，找钩子失败 —— 等很久之后 userhook1 才出现，但一句文本要等很久才出来；
2. Cafe Stella / DRACU RIOT / 白色相簿2：启动后一段时间内**没有任何注入钩子行为**、没有文本，
   连「停止翻译」按钮也无响应；
3. Amakano3：自动带出的 Userhook 完美实时提取 + 翻译（作为对照）。

下面全部是本次在同一台机器上量出来的数字，不是推测；复现脚本在 `_sandbox/`（gitignore）。

## 一、桥接被自己的事件淹了（主因）

| 事实 | 实测 |
| --- | --- |
| 前端每收到一条译文事件就调一次状态查询 | `core/events.js` 的 `vntext:line` → `ctx.vntext.refresh()` → `call("get_vntext_status")` |
| 该状态查询的真实耗时（真应用内量） | **中位 301 ms / 次**（离线单测 113 ms；大头是 `candidate_dirs()` 目录探测 ~100 ms + `ocr.status()` 的 WinRT 调用） |
| 引擎每条发射出的台词都推一次状态 | `vntext.py::_emit()` 末尾 `self._push_status()`（另外还有 17 处） |
| 推送的执行方式 | `gl/api.py::_dispatch_event` → `window.evaluate_js(...)`，**阻塞式**，必须落到 GUI 线程 |
| 原始钩子行的峰值速率（用户日志） | **19 行/秒**（22:22:04），16、12、11 行/秒的秒数很多 |

结论：文本一密，每秒要排队「约 19 次 GUI 往返 + 约 19×301 ms ≈ 5.7 s 的桥接工作量」——
**队列以每秒好几秒的速度堆积**。用户点「发送」「存为专用 hook 码」「停止翻译」时，这些调用排在
几百个 pending 之后，于是表现为「点了没反应」；等几分钟队列排空，userhook1、状态、译文才一起
涌出来。这也解释了「等很久之后一切又正常了」。

## 二、缺字补全跑在取词热路径上，单次 44~68 秒

WillPlus/AdvHD（少女之剑）只有按字形抓的 GDI 钩子，每句都要走
`vntext._promote()` → `memmatch.complete()` 去进程内存里补全整句。实测：

| 场景 | 耗时 |
| --- | --- |
| `memmatch.candidates_ranked(pid, …)` 对真实进程做一次全量扫描 | **44.09 s / 48.30 s / 57.34 s / 61.46 s / 68.28 s**（5 个进程样本） |
| 用户日志里「残片行 → memmatch 完成」的时间差 | **35 s**（22:27:40 → 22:28:15）、**70 s**（22:37:38 → 22:38:48） |
| 一句还没画完时 `complete()` 会 `sleep(0.35)` 再扫一遍 | 最坏 ≈ 2 次全量扫描 |

扫描期间一个核满载、解码+正则持 GIL，取词线程、翻译线程、桥接线程一起被拖慢 ——
这就是「一句要等很久才出来」。

## 三、auto 模式会静默降级到 OCR

「检测到游戏 → 挂上钩子」的耗时逐次统计（`_sandbox/session_latency.py`）：

```
     09-20 21:46:26   （星光咖啡馆）   +115 s
     09-20 22:12:26                    +117 s
     09-21 22:06:38   （DRACU RIOT）    +56 s
     其余 14 次                          0~4 s
```

三次慢的都先出现 `vntext ocr started`，钩子随后才挂上；代码里 `wrong-bitness` /
CLI 未找到 / hook 起不来三条路径都会**不写日志**地掉进 OCR（`vntext.py::start()`），
用户侧只看到「没有任何注入行为」。另外 `find_cli()` 有一条真坑：**显式保存的文件路径优先于
位数**——保存 `x64\TextractorCLI.exe` 而游戏是 32 位时会选中 x64，正好触发 `wrong-bitness`
（用户 22:06 的配置就是 `vntext_tractor_path = E:\Textractor\x64\`）。

## 四、悬浮窗调用可能长阻塞（同一机制的另一极端）

无 GUI 上下文 / 窗口未就绪时实测：

| 调用 | 耗时 |
| --- | --- |
| `Overlay.show()` | **40.02 s**（= pywebview `events.shown.wait(20)` + 创建等待） |
| `Overlay.update()` | **20.01 s / 次**（`evaluate_js` 走 `_pywebview_ready_call` → `event.wait(20)`） |

`start_vntext` 一次要做 `show + update×2`（≈80 s），而 `update()` 还在**每个流式增量**
（`services/vntext.py` 的 `kind == "delta"`）上各调一次。真应用有界面时这次没复现（跑下来一切
正常），但机制相同：一旦悬浮窗的 `_pywebviewready` 没触发或 GUI 线程被占满，每次更新都要付
20 s 的固定代价，而异常被 `except Exception` 吞掉，界面没有任何提示。

## 修复方案（按性价比排序）

| 序号 | 改动 | 预期效果 | 风险 |
| --- | --- | --- | --- |
| 1 | `_push_status()` 合并去抖（如 250 ms 一次）；`vntext:line` 事件里不再调 `get_vntext_status()`，改为直接带 payload 增量更新面板 | 桥接工作量从「19×301 ms/s」降到「4×301 ms/s」，按钮立刻有响应 | 低 |
| 2 | `candidate_dirs()` / `cli_builds()` 结果缓存（如 30 s）；`ocr.status()` 缓存 | 状态查询从 301 ms 降到个位数 ms | 低 |
| 3 | `memmatch` 退出热路径：先查缓存热区，全量扫描改到后台线程并设上限（或仅在前述全部失败时做一次），命中结果按 fragment 缓存 | 缺字引擎从「一句 35~70 s」回到秒级 | 中 |
| 4 | auto 模式不再静默降级：把「为什么走了 OCR」写进日志 + 面板提示；`find_cli` 改为位数优先（显式文件路径与目标位数冲突时以位数为准并记日志） | 「启动后没有任何注入」变成可见、可解释 | 低 |
| 5 | 悬浮窗更新合并 + 不可见时跳过；`update()` 失败只记一次并停用悬浮窗（不再每句付 20 s） | 卡死状态自愈 | 低 |
| 6 | 流式增量的推送节流（如 100 ms 一次，且只推最后一份） | 悬浮窗更新次数降一个数量级 | 低 |

## 第二轮（2026-09-22 凌晨）：引擎级钩子的游戏被「缺字补全」误伤

用户第二轮实测：RIDDLE JOKER / 白色相簿2 无错但「翻页→开始翻译」有明显间隔；DRACU RIOT /
Cafe Stella 从某一句起「提取不到文本」，按「停止翻译」后**一股脑涌出来**；提取一慢，
悬浮窗拖动就卡。

日志（`data/logs/aurora.log`）给出的真凶只有一个：

```
23:52:45 vntext same text merged: '一流のレストランに行くには少々不安かもし…'
23:53:58 memmatch: '一流のレストランに行くには少々不安かもし' -> '耀一流のレストランに…'  ← 73 秒后
23:54:38 vntext same text merged: '「理由はいくつかあるが……」'
23:55:49 memmatch: '「理由はいくつかあるが……」' -> '䐀耀「理由はいくつかあるが……」'      ← 71 秒后
```

| 事实 | 说明 |
| --- | --- |
| KiriKiri/Leaf 这些游戏**同时挂着按字形抓的 GDI 钩子线程** | 那些线程的行也进了缺字补全，于是每句都触发一次全量内存扫描 |
| 单次全量扫描实测 44~68 秒 | 每来一句就新起一个扫描线程 → 十几个扫描并行抢 GIL → 取词/翻译/界面一起被拖死（「停止翻译后一股脑涌出来」「悬浮窗拖动卡」） |
| 补出来的还是**错句** | `耀「理由は…`、`䐀耀「理由は…`：`trim_sentence` 向左回退时把上一段缓冲的垃圾挂到了句首，反而把本来正确的台词替换掉 |
| 白色相簿2 期间没有 memmatch | 它的间隔来自**翻译队列串行**：单 worker + LLM 单句数十秒 → 新句子要等上一句翻完才开始 |

### 本轮的修法

| # | 改动 | 效果 |
| --- | --- | --- |
| 1 | `MEMORY_COMPLETION_SKIP_ENGINES`（TVP/KIRIKIRI、Leaf、BGI、Escu:de、Siglus、CatSystem2/Ares）：这些引擎有引擎级钩子、正文本来就完整，**不做**缺字补全；WillPlus/Artemis 等仍保留 | DRACU RIOT 真机复跑：memmatch **0 行**（此前 3 行、单次 70 秒），文本不再断流 |
| 2 | `memmatch._SCAN_SLOT` 全局扫描闸：同一时间只允许一个内存扫描，排队拿不到就放弃这一句（它已按缺字版正常发射） | 不再出现十几个扫描并行抢 GIL |
| 3 | `trim_sentence` 两条止损：左引号收进来就停；窗口开头多出的**非假名**字（`耀`/`䐀耀`）当缓冲垃圾丢掉 | 补全不再把正确台词替换成 `耀「理由は…`；回归网 `tests/test_memmatch_trim.py` |
| 4 | `LineTranslator` 从单 worker 改成 **2 个 worker**（保留队列语义、不掐断在飞请求，避免「一句有一句没有」） | 真机实测：emit → 译文 2.3~6.7 秒，且下一句**立刻开始**，不再等上一句 |
| 5 | 诊断留痕：`vntext emit [...]`（发射时刻）与 `linetrans done [provider] (N.Ns)`（排队+请求耗时） | 「翻页→看到译文」现在可以直接从日志读出卡在哪一段 |
| 6 | 修 `tools/vntext_live.py`：v2 起设置是独立文件，工具一直从 `library["settings"]` 取 → 自检跑的其实是免费接口 | 自检从此带上用户的 LLM Key（实测 provider 从 `free` 变 `llm`） |

## 第三轮（2026-09-22 00:40）：文学重复被去重吞掉

用户实测白色相簿2：

```
00:37:36 linetrans done [cache] 'とうとう、降ってきた。'
00:38:08 vntext same text merged: 'とうとう、降ってきた。'
```

同一句在剧情里**再次出现**（文学表达），却被「最近 8 条里出现过就丢」这条规则吞掉 ——
那条规则**没有时间窗**，所以隔多久都算重复。

修法：`VnTextEngine.SHORT_DUP_SECONDS = 10.0`，`_recent_text` 从「纯字符串列表」改成
`(文本, 到达时刻)` 并按时效剪枝。钩子侧的真重复（多线程/重绘重发）都在几秒内到达，
10 秒足够挡；隔半分钟再出现的同一句是正文，照常发射（译文命中缓存，瞬间返回）。
回归网：`tests/test_repeat_dialogue.py`（隔 32 秒必须再发一次 / 即时重发仍要挡）。

## 第四轮（2026-09-22）：交接文档里那两条高优先级遗留项

这两条不是新事故，是前几轮修完后**如实登记在待办里**的尾巴：① 缺字补全彻底异步化；
② 冷启动宽限期。都在「游戏内翻译」这一条链路上，一起做、一起验。

### ① 补完版不再只进缓存，而是作为「同一句的新版本」补发

第三轮把缺字补全改成「最多等 2.5 秒 + 后台继续扫 + 结果进缓存」，取词热路径不再被
44~68 秒的全量扫描堵住。但**这一句本身**还是停在缺字版上：扫出来的完整版只在
「同一句下次再出现」时才用得上，如果那句剧情只出现一次，用户永远看不到完整译文。

| # | 改动 | 说明 |
| --- | --- | --- |
| 1 | `memmatch.complete_async/snap_async` 增加 `on_done` 回调 | 后台扫出结果时回调（固定早于等待者返回，避免「同步拿到」被误当成迟到的补完版） |
| 2 | `VnTextEngine._arm_completion` / `_attach_completion` / `_resolve_completions` | 扫描前**先登记认领**（认领时刻之后发射的缺字版才有资格被认领 —— 同步拿到结果的那次缺字版压根没发射，登记会自然过期）；扫出结果后挂在登记上，由 `_flush_loop` 串行补发 |
| 3 | 发射带 `id`（进程级递增）与 `revise_of` | 补发语句 = 「某条已发射行的补完版」，认领窗口 `COMPLETION_CLAIM_TTL = 150s`（要盖住 44~68 秒的扫描），发射记录只留最近 128 条 |
| 4 | `LineTranslator` 按序号**原位替换**历史 | 面板不会出现「残句 + 完整句」两条；缺字版的译文要是后到（LLM 慢）直接丢掉，不再把完整译文顶回去 |
| 5 | 旧台词的补发走 `silent` | 补发到达时玩家往往已经翻页：不是当前那句就只修面板历史，不把悬浮窗顶回旧台词 |

### ② 冷启动宽限期（前 30 秒门禁放宽）

真机自测里出现过「原始行审计报漏掉 N 条」，逐条过规则却是正经台词：丢在**更前面的
线程门禁** —— 测试脚本在游戏刚起来、领跑线程还没选出来时连点 6 次，那几句只从非领跑
线程经过，按设计被当成「弱行」（没有句读、又不是领跑线程）丢掉了。

修法：`VnTextEngine.COLD_START_GRACE = 30.0`，会话开始 30 秒内**只挡不像台词的行**，
台词照收（去重/并合照常，同一句从两条线程来仍只翻一次）。宽限期只对走过 `start()`
的会话生效，自检脚本直接喂行时行为完全不变。日志关键字：`vntext gate held (cold start)`；
状态里 `cold_passes` 记放行条数。
