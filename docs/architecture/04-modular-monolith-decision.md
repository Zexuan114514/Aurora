# 04 单体 / 模块化单体判定（monolith-vs-modular-monolith-reviewer）

## Summary

**结论：留在「单进程 + 模块化单体」，不做服务拆分，也不拆子系统进程。** 理由是分发形态、团队规模与
故障模式三者都指向同一答案；只有当出现明确的触发条件（见文末）时才重新评估。

## Decision framing

| 判据 | 现状 | 指向 |
| --- | --- | --- |
| 系统范围 | 单机桌面启动器：库管理、元数据、启动、翻译 | 单体 |
| 团队与所有权 | 单人维护 + 社区提交 PR | 单体（模块边界靠代码约定） |
| 部署与伸缩需求 | 免安装单 exe；无并发用户、无水平伸缩 | 单体 |
| 变更模式 | 高频：引擎规则、资料源、界面；低频：存储格式、启动流程 | 模块化（高频部分要有扩展点） |
| 故障模式 | 高风险代码是调试器/内存扫描/OCR，但仅按需运行 | 暂不拆进程 |
| 外部集成数量 | 11 处（HTTP / 子进程 / Win32 / 系统组件） | 端口适配是刚需 |

## Option comparison

| 形态 | 收益 | 代价 | 判定 |
| --- | --- | --- | --- |
| 保持现状（无结构） | 零投入 | 改动风险与日俱增，社区无法贡献 | ❌ |
| **模块化单体**（分层 + 端口 + 规则包） | 边界清楚、纯逻辑可测、扩展点明确、发布形态不变 | 需要一次性迁移（P0–P7）与守卫 | ✅ 采用 |
| 拆出文本/翻译子进程 | 崩溃隔离、可单独重启 | IPC 自研、打包与排错变复杂、Textractor 本身已是子进程 | ⏸ 备选 |
| 拆成主进程 + 常驻服务 | 多窗口 / 后台复用 | 需要框架依赖、端口与鉴权、安装形态重做 | ❌ 当前不需要 |

## 模块边界判定（哪些该合、哪些该分）

- **该合的**：`library` 与 `settings` 共用一份状态写入通道（单写者），否则会出现「设置写丢游戏库」这类竞态。
- **该合的**：文本清洗规则与引擎规则同属 `domain`，因为规则要靠真机样本一起回归。
- **该分的**：`domain` 与 `infra`（纯规则 vs 子进程/HTTP/Win32），这是当前最痛的一刀。
- **该分的**：`bridge`（参数整形 + 事件回推）与 `app`（用例编排），否则契约永远绑死在业务上。
- **不该分的**：资料源不拆服务，用 `MetadataSource` 端口 + 注册表即可；插件走目录加载，不走网络。

## Evidence vs assumptions

- **证据**：外部集成与线程清单来自代码扫描；故障模式判断基于 `hookfinder` 只在用户手动触发时运行、
  `vntext` 的崩溃日志（`data/aurora.log`）没有出现「主进程被 native 打崩」的记录。
- **假设**：未来 12 个月仍以单人维护为主；社区贡献以「资料源 / 引擎规则 / 翻译引擎」为主，而不是核心重构。
- **不确定**：Windows OCR / Textractor 在极端场景的稳定性没有长时间压测数据 → 作为 R7 的实验项跟踪。

## Risks or tradeoffs

| 风险 | 触发信号 | 处理 |
| --- | --- | --- |
| 同进程高风险代码打崩主进程 | 连续两次崩溃日志指向 hookfinder / memmatch | 启动选项 C：把文本链路拆子进程（`01` 选项 C） |
| 单写者成为瓶颈 | 大量设置变更导致 UI 卡顿 | 去抖 + 只写变更文件（P2 已覆盖） |
| 模块边界腐化 | AST 守卫失败或出现跨层 import 例外 | 守卫进 CI；例外必须写 ADR |
| 社区 PR 改核心文件 | 反复出现同区域的冲突 | 把该区域改为规则包 / 插件点，而不是加更多分支 |

## 何时重新评估（可执行触发条件）

1. 主进程因 native 代码崩溃 ≥ 2 次且能在日志里定位到本仓库的模块。
2. 出现「后台常驻 / 多窗口 / 第三方程序调用 Aurora 能力」的真实需求。
3. 明确要做跨平台（当前 Windows-only 的假设不再成立）。
4. 游戏库规模中位数超过 500 款，且 `10` 中的热点缓解手段失效。
